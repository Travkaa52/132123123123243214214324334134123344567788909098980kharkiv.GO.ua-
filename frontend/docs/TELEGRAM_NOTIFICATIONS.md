# Сповіщення з Telegram-каналів (без логіну, без бекенда)

Розділ «Сповіщення» на головній сторінці показує останні пости з обраних
Telegram-каналів. Працює повністю через GitHub Actions — без окремого
сервера, без входу в Telegram-акаунт, без api_id/api_hash, без коду
підтвердження чи пароля.

## Як це працює

1. У Telegram будь-який публічний канал має відкриту прев'ю-версію за
   адресою `https://t.me/s/<username>` — саме її бачить людина без
   Telegram, коли переходить за посиланням на канал з браузера.
2. `scripts/parse-telegram-channels.mjs` періодично (кожні 10 хв, за
   розкладом у `.github/workflows/telegram-notifications.yml`) забирає ці
   сторінки звичайним HTTP-запитом, розбирає останні пости і зберігає їх у
   `public/data/notifications.json`.
3. GitHub Actions сам комітить оновлений файл назад у репозиторій.
4. Фронтенд (Vite) роздає цей файл як звичайний статичний JSON — жодного
   бекенда тримати не треба, `src/api/notifications.ts` просто робить
   `fetch('/data/notifications.json')`.

Користувач застосунку про це ніяк не знає — він просто бачить готову
стрічку сповіщень на головній сторінці.

## Структура репозиторію

Workflow-файл написаний під структуру, де фронтенд лежить у підпапці
`frontend/` репозиторію (як у `rharkivGOO/frontend/...`) — саме так
влаштований цей проєкт. Тобто в репозиторії має бути:

```
rharkivGOO/
├── .github/workflows/telegram-notifications.yml
└── frontend/
    ├── scripts/parse-telegram-channels.mjs
    └── public/data/notifications.json   ← сюди пишеться результат
```

**Якщо у вас інша структура** (наприклад, фронтенд лежить прямо в корені
репозиторію, без папки `frontend/`) — відкрийте
`.github/workflows/telegram-notifications.yml` і приберіть звідти
`working-directory: frontend` та префікс `frontend/` у шляхах
(`frontend/scripts/...` → `scripts/...`, `frontend/public/data/...` →
`public/data/...`).



У репозиторії на GitHub: **Settings → Secrets and variables → Actions**.

**Канал `kh_metro` (офіційний Харківський метрополітен) підключено за
замовчуванням** — він завжди парситься, навіть якщо `TELEGRAM_CHANNELS`
взагалі не задано. Це основне джерело термінових оголошень для розділу
"Живе метро" (зупинка/обмеження руху, закриття станцій, повітряна тривога
тощо), тому воно не повинно залежати від налаштування репозиторію.

Щоб **додати** інші канали, вкажіть їх через `TELEGRAM_CHANNELS` — вони
приєднаються до `kh_metro`, а не замінять його:

| Ім'я | Значення | Приклад |
|---|---|---|
| `TELEGRAM_CHANNELS` (опційно) | Юзернейми додаткових каналів через кому, без `@` або з ним — обидва варіанти працюють | `kharkivgo_news,kharkiv_transport` |
| `TELEGRAM_CHANNELS_REPLACE` (опційно) | `1` — повністю замінити список каналів значенням `TELEGRAM_CHANNELS` (тобто прибрати `kh_metro` за замовчуванням, якщо він не потрібен) | `1` |
| `NOTIFICATIONS_LIMIT` (опційно) | Скільки останніх постів тримати з кожного каналу | `15` (за замовчуванням) |

Все. Ніяких токенів, паролів, номерів телефону чи кодів підтвердження не
потрібно — все інше `permissions: contents: write` у workflow-файлі вже
дозволяє Action комітити файл назад автоматично через вбудований
`GITHUB_TOKEN`.

## Класифікація повідомлень @kh_metro

Для офіційного каналу метрополітену парсер додатково розпізнає:

- `kind: "alert"` — термінове оголошення (зупинка/обмеження руху,
  закриття станції чи вестибюля, повітряна тривога, аварія) чи
  `"info"` — звичайна новина. Визначається за ключовими словами в тексті
  (з урахуванням відмінків української мови).
- `lineIds: string[]` — які лінії метро (`route-metro-1/2/3`) згадані в
  тексті, якщо вдалось розпізнати.

У розділі "Сповіщення" термінові оголошення (`kind: "alert"`) підіймаються
над рештою стрічки та підсвічуються червоним, а дзвіночок у шапці починає
пульсувати, поки користувач їх не побачив. Для решти каналів ці поля не
заповнюються.

## Перший запуск

Actions спрацює сама за розкладом (`cron: '*/10 * * * *'`), або запустіть
вручну: вкладка **Actions** → **Telegram notifications feed** → **Run
workflow**.

## Якщо фронтенд задеплоєний окремо від репозиторію

Якщо сайт хоститься не з того самого білда, де лежить
`public/data/notifications.json` (наприклад, деплой підхоплює тільки
`dist/` без свіжих комітів), задайте у `.env` фронтенда:

```
VITE_NOTIFICATIONS_URL=https://raw.githubusercontent.com/<ваш-акаунт>/<репозиторій>/main/public/data/notifications.json
```

або URL на GitHub Pages, якщо він увімкнений для репозиторію.

## Обмеження підходу

- Працює тільки з **публічними** каналами (приватні тут в принципі
  недоступні без входу в акаунт — і це нормально, для приватних каналів
  потрібен зовсім інший, значно складніший підхід з логіном).
- Максимальна частота оновлення обмежена лімітами GitHub Actions cron
  (мінімум практично ~5 хв між запусками) — для стрічки новин каналу цього
  більш ніж достатньо.
