# ⚠️ Критично: знайдено відкритий service_role ключ

У завантаженому архіві в `supabase/` лежав текстовий файл з відкритим
Supabase URL, `anon`-ключем і, найважливіше, **`service_role`-ключем**.

`service_role` повністю обходить RLS — будь-хто з цим ключем має необмежений
read/write доступ до всієї бази, включно з таблицями, які RLS мав би
приховувати (`delay_reports`, а тепер і `profiles`/`favorites`/`history`).

**Я видалив цей файл з переданого назад архіву** і ніде не використав ці
значення в коді. Але якщо цей файл хоч раз потрапляв у git-репозиторій
(навіть у приватний) або пересилався будь-де — ключ треба вважати
скомпрометованим.

## Що зробити зараз

1. **Ротуйте ключі**: Supabase Dashboard → Project Settings → API →
   "Reset service_role key" (і за потреби `anon` теж).
2. Якщо файл потрапляв у git — видаліть його з історії
   (`git filter-repo` / BFG), а не просто новим комітом.
3. Service_role ключ має жити **тільки** в secrets Edge Functions
   (`supabase secrets set SUPABASE_SERVICE_ROLE_KEY=...`) і в змінних
   середовища бота/GitHub Actions — ніколи у файлах репозиторію, ніколи у
   фронтенді.
4. Додайте у `.gitignore` будь-які `*.txt`/нотатки з ключами, якщо такі
   файли створюються локально під час роботи.
